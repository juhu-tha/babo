## 1. Mischungsberechnung – Ursachen der langen Tasks

Trace der vorgerenderten Seite `/modul/mischungsberechnung` (vorher, mit Trace-Aufschlag):

| Task (nach FCP) | Dauer | Ursache |
|---|---:|---|
| Auswerten des Einstiegs `app` | 130–220 ms | React, ReactDOM, App-Rahmen, Registry-Auszug in **einem** Modul-Graphen (Parse/Compile ≈ 70 ms) |
| Austausch der statischen Seite durch React | 190–270 ms | Commit von ≈ 800 Layout-Objekten; Layout 110–180 ms, erzwungen durch die Lagemessung in `NachErstemBild`. Rund die Hälfte davon: erste Eingabekarten, Ergebniskarte, Fußzeile (mobil alle unterhalb des Bildausschnitts) und die **geschlossene mobile Seitenleiste** (≈ 350 Elemente Menü, inert, außerhalb des Bildes) |
| Abschnitte (`NachErstemBild`) | 65–145 ms je Abschnitt | Rendern; davon ≈ 80 ms Zahlformatierung: `toLocaleString` legt bei jedem Aufruf ein neues `Intl.NumberFormat` an (Regler, Ergebnistabelle, Rechenweg) |
| KaTeX | 90–115 ms + 70–115 ms | Auswerten des KaTeX-Chunks (≈ 90 ms) und Rendern der Formeln – obwohl die beiden Formeln der Seite mobil bei 6700 und 9100 px liegen |
| Schrift Inter einsetzen | 115–160 ms | Neu-Layout der ganzen Seite (≈ 2300 Layout-Objekte) |
| Rest | je 50–100 ms | Stil/Layout beim progressiven Aufbau der statischen Seite, `useAutoFormLabels` (Scroll-Prüfung erzwingt Layout) |

Diagramme (Chart.js) waren schon bedarfsgesteuert (nur in Sichtnähe) und spielen keine Rolle.

## 2. Startseite – LCP

Diagnose: LCP = FCP = Startseiten-Schale; sie brauchte HTML **und das ganze Stylesheet** (374 kB roh, 43 kB Brotli). Das CSS teilte sich unter der Drosselung die Bandbreite mit dem Einstieg (110 kB gzip) und den vorgeladenen Startseiten-Chunks und war erst nach ≈ 1,75 s da (FCP ≈ 2,0 s lokal, live +0,4 s). Das Stylesheet stand außerdem erst hinter der 31-kB-Vorlade-Karte. Probe „nur Karte hinter das CSS“: −0,08 s – zu wenig.

Maßnahme M6 – **kritisches CSS der Schale** (`scripts/kritischesCss.ts`, Vite-Plugin):

- Im Kopf von `dist/index.html` steht an Stelle des Stylesheets `<style data-bb-kritisch>` mit allen Regeln, die ein Element der Schale (oder `<html>`/`<body>`) treffen können: 63 kB roh, 9,6 kB Brotli. Auswahl großzügig: Eine Regel entfällt nur, wenn jeder Selektor eine Klasse verlangt, die in der Schale nicht vorkommt (Klassen in `:is()/:where()/:not()/:has()` zählen nicht), oder ein `[class*=…]`-Vergleich keinen Treffer haben kann; `@font-face`/`@keyframes` entfallen, alles andere bleibt in Originalreihenfolge. Die Klassen `dark` und `bb-breite-*` (Boot-Skript) gelten immer als vorhanden.
- Das vollständige Stylesheet steht unverändert direkt hinter `<div id="root">`. Dort hält es nur den Parser an, nicht das Zeichnen der Schale davor. Skripte – auch der Einstieg – laufen erst, wenn es geladen ist: React rendert nie ohne volles CSS (geprüft: beim ersten Einhängen von React ist das Stylesheet in allen Fällen geladen – Startseite, Modulseite, `/#glas`, Alias `/#lca`, dunkel).
- Ohne JavaScript lädt das Stylesheet normal. Keine Änderung an Inline-Skripten, keine neuen CSP-Hashes (`style-src` erlaubt Inline-Stile schon); `npx tsx scripts/vercelKonfig.ts` meldet „vercel.json aktuell“.
- Vorgerenderte Modulseiten entstehen aus `dist/index.html` und stellen den alten Kopf wieder her (`kritischEntfernen` in `scripts/vorrendern.ts`) – ihre Schale ist der Modulinhalt.
- Prüfung im Browser (ohne React): berechnete Stile aller 158 Elemente der Schale und Bildschirmfoto mit nur kritischem CSS gegen volles Stylesheet – **0 Abweichungen, Bild pixelgleich** in hell/dunkel × mobil/breit × Seitenbreite standard/breit/voll (8 Kombinationen). Tests: `tests/kritischesCss.test.ts` (Auswahl, Reihenfolge, Umkehrbarkeit, gebaute Seiten).

Die Startschale selbst ist unverändert (kein Neuerzeugen nötig).
